דוח בדיקת חדירות עבור CrossGuard-AI

תאריך הדוח: 2026-05-03

יעד הבדיקה: http://192.168.190.129:3000

תקציר מנהלים

דוח זה מציג את ממצאי בדיקת החדירות האוטומטית שבוצעה כחלק מפרויקט CrossGuard-AI, כנגד היישום בכתובת http://192.168.190.129:3000. תהליך הבדיקה כלל שלבים אוטומטיים מתקדמים:

  1. סריקה ראשונית: שימוש בכלי סריקה כגון ZAP (OWASP ZAP), Nuclei ו-Dirb לזיהוי חולשות נפוצות ונקודות תורפה.
  2. ניתוב והתאמה: מנוע AI ניתח את ממצאי הסריקה והתאים אוטומטית כלי ניצול ייעודיים (Exploit Tools) בהתאם לחולשות שזוהו.
  3. שלב הניצול (Exploitation): הפעלת כלי ניצול ממוקדים לביצוע תקיפות, כולל SQLMap, כלי לחטיפת חשבונות אדמין, מנגנון יצירת XSS ממוקד יישומי SPA, כלי לחילוץ קבצים מקומיים (LFI) וכלי לחילוץ נתונים מ-FTP.

הבדיקה גילתה מספר חולשות קריטיות שנוצלו בהצלחה, כולל: הזרקת SQL שהובילה לחשיפת טבלאות מסד נתונים, פריצה לחשבון מנהל מערכת (אדמין) וחטיפת טוקן JWT, קריאת קבצים שרירותית שאפשרה חשיפת קובצי קונפיגורציה פנימיים, ו-דליפת נתונים קריטית של קבצים רגישים, כולל מאגר סיסמאות KeePass, מתוך תיקיית FTP חשופה. ממצאים אלו מצביעים על סיכונים משמעותיים לאבטחת היישום ודורשים טיפול מיידי.

6. כלי לניצול XSS (XSS Weaponizer)

המערכת יצרה 20 קישורים ממוקדים לניצול חולשות XSS מבוססות DOM ביישום. קישורים אלו מיועדים לבדיקה נוספת במודל זיהוי ה-CrossGuard-AI. להלן מספר דוגמאות ל-payloads שנוצרו:

  • <script>alert("XSS_1_Classic")</script>
  • <img src="x" onerror="alert('XSS_2_Image')">
  • <svg onload="alert('XSS_3_SVG')">
  • <iframe src="javascript:alert('XSS_4_Iframe')">
  • {{constructor.constructor("alert('XSS_16_Angular_Bypass')")()}} (ליישומי Angular)

מסקנות והמלצות

ממצאי בדיקת החדירות מצביעים על חולשות אבטחה משמעותיות וקריטיות במערכת, אשר נוצלו בהצלחה. טיפול מיידי בחולשות אלו הוא הכרחי למניעת פגיעה באבטחת המידע ושלמות המערכת.

המלצות לתיקון:

  1. הזרקת SQL (SQL Injection):
    • ולידציה של קלט: יש לבצע ולידציה קפדנית של כל קלט משתמש בצד השרת לפני השימוש בו בבסיס הנתונים.
    • שימוש ב-Parameterized Queries / Prepared Statements: יש להטמיע את עקרונות ה-Parameterized Queries או Prepared Statements עבור כל אינטראקציה עם מסד הנתונים.
    • ORM (Object-Relational Mapping): שימוש ב-ORM מספק שכבת אבטחה נוספת מפני הזרקות SQL.
    • WAF (Web Application Firewall): הטמעת WAF יכולה לסייע בזיהוי וחסימת ניסיונות הזרקת SQL.
  2. פריצה לחשבון מנהל מערכת ודליפת JWT:
    • מדיניות סיסמאות חזקה: יש לאכוף מדיניות סיסמאות מורכבות, כולל אורך מינימלי, תווים מיוחדים ואיסור שימוש בסיסמאות נפוצות.
    • אימות רב-שלבי (MFA): הטמעת MFA עבור חשבונות אדמין.
    • הגבלת קצב (Rate Limiting) והגנה מפני Brute-Force: יש להגביל את מספר ניסיונות ההתחברות ולחסום כתובות IP חשודות.
    • אחסון סיסמאות מאובטח: יש לוודא שהסיסמאות מאוחסנות באופן מוצפן (Hash ו-Salt) ולא בטקסט רגיל או ב-Hash חלש.
    • ביטול תוקף JWT: הטמעת מנגנון לביטול תוקף טוקני JWT במקרה של התנתקות משתמש או חשד לפריצה.
  3. חולשות Cross-Site Scripting (XSS):
    • קידוד פלט (Output Encoding): יש לקודד את כל הקלט המבוסס על משתמשים לפני הצגתו בדפדפן, בהתאם להקשר ה-HTML.
    • ולידציה של קלט (Input Validation): ולידציה קפדנית של קלט בצד השרת כדי למנוע הכנסת קוד זדוני.
    • Content Security Policy (CSP): הטמעת כותרת CSP חזקה יכולה להגביל את המקורות מהם ניתן לטעון סקריפטים ומשאבים אחרים.
    • Sanitization: יש להשתמש בספריות אבטחה לצורך ניקוי קלט ממשתמשים המכיל HTML.
  4. קריאת קבצים שרירותית (Arbitrary File Read / LFI):
    • ולידציה קפדנית של נתיבים: אין לאפשר קלט משתמש ישיר בבניית נתיבי קבצים. יש להשתמש ב-Whitelisting עבור קבצים ותיקיות מורשים בלבד.
    • הגבלת הרשאות: לוודא שהתהליכים הרלוונטיים פועלים עם הרשאות מינימליות (Least Privilege) כדי למנוע גישה לקבצים שאינם נחוצים.
    • מניעת Null Byte Injection: לוודא שהמערכת מטפלת כראוי בתווי Null Byte (%00) בקלט, ואינה מאפשרת להם לעקוף מסננים.
  5. חשיפה קריטית של קבצים (Exposed Data Leakage / Security Misconfiguration):
    • הגבלת גישה לתיקיות רגישות: יש להגביל את הגישה לתיקיית /ftp וכל תיקייה אחרת המכילה קבצים רגישים או קבצי גיבוי. גישה צריכה להיות רק למשתמשים מורשים ובאמצעות פרוטוקולים מאובטחים (כגון SFTP ולא FTP חשוף).
    • הסרת קבצי גיבוי וקונפיגורציה: יש להסיר את כל קבצי הגיבוי (כגון .bak), קובצי קונפיגורציה, קוד מקור או כל קובץ אחר שאינו מיועד לחשיפה ציבורית מהשרת.
    • אבטחת מאגרי סיסמאות: קובץ incident-support.kdbx (מאגר סיסמאות KeePass) אסור בשום אופן להימצא בשרת ווב חשוף. יש להעביר אותו מיד למקום מאובטח ביותר עם בקרות גישה הדוקות והצפנה חזקה.
    • בדיקות תצורה תקופתיות: יש לבצע סקירות אבטחה קבועות לתצורת השרת והיישום כדי לזהות ולתקן הגדרות שגויות.
  6. המלצות כלליות:
    • עדכון רכיבים: יש לוודא שכל הרכיבים, ספריות, פלטפורמות ומערכות הפעלה המשמשים ביישום ובשרת מעודכנים לגרסאות האחרונות עם תיקוני האבטחה הרלוונטיים.
    • פיתוח מאובטח (Secure Development Lifecycle): הטמעת עקרונות פיתוח מאובח בחיי מחזור הפיתוח של היישום.
    • בדיקות חדירות תקופתיות: המשך ביצוע בדיקות חדירה ידניות ואוטומטיות באופן סדיר.
